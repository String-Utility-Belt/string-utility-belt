## What is SQL formatting?

A SQL query written on one line, or generated by an ORM without any regard for readability, is hard to scan and hard to review in a diff. This tool pretty-prints SQL (breaking clauses like `SELECT`, `FROM` and `WHERE` onto their own lines, indenting selected columns, and normalizing keyword case) using the `sql-formatter` library under the hood, the same job a query formatter built into a database GUI does.

## How it works

The formatter parses the query for the chosen dialect, then rebuilds it clause by clause, indenting the parts of each clause and putting keywords in the chosen case:

```example
title: default dialect, upper keywords
input: select a,b from t where a=1
output: SELECT
  a,
  b
FROM
  t
WHERE
  a = 1
```

Because different databases extend standard SQL differently (square-bracket identifiers in T-SQL, backtick identifiers in MySQL, `::` casts in PostgreSQL), the **dialect** option tells the parser which syntax to expect:

```example
title: transactsql dialect understands [bracketed] identifiers and TOP
params: {"dialect": "transactsql"}
input: select top 1 [name] from [dbo].[users]
output: SELECT
  TOP 1 [name]
FROM
  [dbo].[users]
```

Keyword case can be forced to uppercase (the default), lowercase, or left exactly as typed. Only keywords are affected: function names and data types keep the case you wrote, so `select count(*)` becomes `SELECT count(*)`:

```example
title: lowercase keywords
params: {"keywordCase": "lower"}
input: SELECT id FROM users
output: select
  id
from
  users
```

Multiple statements separated by semicolons get blank lines between them, controlled by **blank lines between queries**. Set it to `0` to keep statements adjacent:

```example
title: no blank line between statements
params: {"linesBetweenQueries": 0}
input: select 1; select 2;
output: SELECT
  1;
SELECT
  2;
```

## Options

- **dialect**: one of `sql` (generic, the default), `mysql`, `postgresql`, `sqlite`, `mariadb`, `bigquery`, `spark` or `transactsql`. An unrecognized value falls back to the generic `sql` dialect rather than raising an error.
- **keyword case**: `upper` (the default), `lower` or `preserve` (leave keywords exactly as written). Function names, data types and identifiers are never re-cased.
- **indent width**: spaces per nesting level, from 0 to 16. The default is 2; `0` removes indentation but keeps the line breaks between clauses. Negative values are clamped to 0 rather than causing an error.
- **blank lines between queries**: how many blank lines separate statements when a query string has more than one, from 0 to 10. The default is 1.

## Common uses

- Cleaning up a query copied from an ORM's debug log or a database GUI's history before pasting it into a code review.
- Standardizing formatting across a team's `.sql` migration files.
- Making a long, deeply nested query with subqueries and joins easier to read before optimizing it.

## Tips and pitfalls

- Formatting is dialect-aware but not a full validator: some genuinely invalid SQL for a dialect (an unterminated string, unmatched parentheses) raises a specific parse error naming the problem; other unusual syntax may format without complaint even if the database itself would reject it.
- Non-ASCII text inside string literals, including emoji, passes through unchanged.
- To collapse a formatted query back onto one line instead, see [sql minify](/util/sql_minify/); to escape a value for a SQL string literal, see [sql escape](/util/sql_escape/) (parameterized queries remain the safer way to pass values).
